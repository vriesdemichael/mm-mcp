# ADR-023: Distributed as signed binaries, .mcpb bundles, a container image, and through the MCP Registry

Each release publishes, on its GitHub release, a static mm-mcp binary for Linux, macOS and Windows on amd64 and arm64, each alone in an archive, with an SPDX SBOM; a .deb and an .rpm for each Linux architecture; a checksum manifest; and an .mcpb bundle per platform, which Claude Desktop installs with one click and which asks for every setting a person makes: the Mattermost address, the token, whether to allow writes, whether to mark posts as written with AI, and whether to reach the computer's files and where to save them. The archives, packages, bundles and the manifest are signed with keyless Sigstore bundles, and each binary's SBOM is attested against its archive and packages after tools/sbom-check has held it to the binary. The binaries are built reproducibly, with no symbol tables and an empty build id, and the Windows binary carries version information: a Go binary whose hash changes on every build, or that names nothing about itself, is what Defender's machine-learning heuristics and SmartScreen's reputation flag. server.json is published to the MCP Registry as `io.github.vriesdemichael/mm-mcp`, naming the bundles by their download address and checksum, and the environment variables each takes.

Each release is also a container image on GitHub Container Registry, `ghcr.io/vriesdemichael/mm-mcp`, tagged with the version and `latest`, one tag holding linux/amd64 and linux/arm64: GoReleaser's Linux binary on distroless's static base, running as a user that is not root, with no shell. The base is pinned by digest, and CI and the release verify distroless's own keyless Sigstore signature on it before building on it (`task release:image:base:verify`); Dependabot moves the digest, and its update merges itself once CI passes (ADR-012). A new digest releases nothing by itself: it ships in the next release's image. image/Dockerfile runs no command at build time, so building for the other architecture needs no emulator, and every file in the image is stamped with the commit's time, so the same commit builds the same digest. The image is built once every check on the archives has passed, pushed by its digest alone, signed with keyless Sigstore, given its build provenance and each platform's SPDX SBOM, scanned from the image, as attestations in the registry, and tagged only then, just before the release is made public. server.json lists it as an `oci` package beside the bundles, by its version's tag, with the bundle's variables less the ones that name a path on the person's machine and MM_MCP_LOCAL_FILES, which the image sets off (ADR-029). The registry reads the image's `io.modelcontextprotocol.server.name` label without signing in, and GitHub Container Registry makes a new package private, so the first release stops before publishing server.json until the package is made public. The image serves stdio, `docker run -i`, only: its HTTP transport listens on a loopback address, which a container cannot publish, until it authenticates its clients (ADR-020).

The bundles and server.json carry the version 0.0.0 in the repository and are stamped by the release workflow (ADR-013), so a version is written in one place, the tag. CI builds the archives, the bundles and the image for both platforms on every pull request, checks a bundle with the official mcpb tool, and serves an image built around the change's mm-mcp against a real Mattermost (`task test:image`).

When a variable is added, document it on the configuration page and add it to the bundle's user configuration and env in mcpb/manifest.json. tools/mcpb writes server.json's environment variables from the manifest, so the registry entry declares what the bundle asks for, and `TestTheBundleSetsEveryVariableAPersonConfigures` holds the manifest to the variables mm-mcp reads (ADR-015).

Homebrew, Scoop and WinGet are published once the release is public, never from the draft. tools/packages writes the formula for the vriesdemichael/homebrew-tap tap and the manifest for the vriesdemichael/scoop bucket from the release's checksum manifest, and Komac, run as its released binary held to the release's checksums, opens the pull request to microsoft/winget-pkgs from a fork kept level with upstream; winget-releaser, which wraps Komac, installs it with an action pinned to a branch, which this repository refuses. Each pushes with its own token, which the workflow gives only to the step that pushes, and a pull request writes the formula and the manifest from its snapshot so a release writes nothing a pull request has not. WinGet's first version is submitted by hand; the job publishes from the second on.

A static binary needs no runtime on the person's machine, and the bundle and the registry are where MCP clients look a server up. A bundle's manifest names its operating system but not its architecture, so a client installing from the registry cannot tell the amd64 bundle from the arm64 one; one image tag carries both, and the container runtime picks. The image is for such a client, and later for hosting a server beside Mattermost; for a client that starts mm-mcp itself, the binary and the bundle start at once, need no container runtime, and run on the person's machine, as a server over stdio is taken to. Signatures and attested SBOMs let an organisation that admits software through review check what it runs.

## Not chosen

- **One universal bundle**: A bundle holds one binary, and a person installs the one for their machine.
- **GoReleaser's dockers_v2**: It pushes the image, tagged, in the run that drafts the release, before the SBOMs are checked, so a tag could name a release that a later check refuses; and its snapshot builds one image per platform rather than the image a release pushes.
- **BuildKit's own provenance and SBOM**: They are unsigned, and BuildKit fetches the SBOM's scanner as an image of its own at build time; the release attests both with Sigstore, as it does the archives.
- **An image from scratch**: It would need the certificate authorities, the time zones and a user copied in from somewhere; distroless's static image is that, maintained and pinned by digest.
- **The image as the way to install mm-mcp**: A container starts slower than a binary, needs a runtime, and has a disk that is not the person's, which a server over stdio is taken to have.
- **GoReleaser's own Homebrew, Scoop and WinGet publishing**: It publishes in the run that drafts the release, before the SBOMs are checked, so a tap or a bucket could name a release that a later check refuses and nobody can download.
